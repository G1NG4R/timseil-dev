## What the grid shows

`/api/systems/timseil-dev?window=91`, read on 23 October 2026 at 22:10Z, has
five days in state `outage`:

```
2026-09-05  downSec 16348
2026-09-25  downSec  5400
2026-09-26  downSec  2529
2026-10-10  downSec  6600
2026-10-11  downSec  3178
```

The probe's log, `uptime-log.txt` on the `ops-data` branch, has three pairs of
lines behind them:

```
2026-09-05T01:10:23Z  down  http 4xx
2026-09-05T05:42:51Z  up
2026-09-25T22:28:40Z  down  probe failed
2026-09-26T00:45:49Z  up
2026-10-10T22:06:52Z  down  http 4xx
2026-10-11T00:54:50Z  up
```

Three events, five cells, because a day in the grid is a UTC day and two of the
events started before midnight.

## The part all three share

The probe is a scheduled GitHub Actions workflow, `probe.yml`, declared every
five minutes. Between each `down` and the `up` after it, the workflow did not
run at all:

| Incident | `down` run | `up` run | Runs in between | Gap |
|---|---|---|---|---|
| INC-001 | `33935340257` | `33947920204` | 0 | 4 h 32 min |
| INC-002 | `36196883804` | `36206021695` | 0 | 2 h 17 min |
| INC-003 | `38090181603` | `38100026694` | 0 | 2 h 48 min |

The replay expands a `down`/`up` pair onto the probe interval, and the roll-up
sums the time between checks. So one failed request followed by a silent cron
becomes hours of outage. #180 fixed the arithmetic, so the duration is no
longer a count times a constant. The grammar is still open: a stretch nobody
measured is counted as down. That is #505.

So every `downSec` above is the length of a gap in the measurement. It is not
the length of an outage. How long the site was actually unreachable is unknown
in all three cases, and it may be zero.

## INC-001 · 5 September, 01:10:23Z

The probe's request was answered `403` and the probe wrote `down`.
`http 4xx` is the only word it has for a refusal.

The request never reached the site. The proxy's router counter for the web
route moved from 3499 to 3500 refused requests in the scrape at 01:10:30Z. The
service counter behind it recorded nothing in that minute. Loki has no line from
the web container between 01:08 and 01:13. Both containers had been running for
eighteen hours, and the last deploy had finished at 00:02:30.

**Cause:** the probe was turned away before its request reached the site, and
the site kept serving throughout.
**Fix:** nothing on the site. The probe still cannot tell a refusal from an
absence, and it still counts a gap as duration (#505).

## INC-002 · 25 September, 22:28:40Z

Deploy `a66c2f0` (#412) reported at 22:28:30Z. Ten seconds later the probe's
request failed with `probe failed`. That is the probe's word for an answer it
has no more specific name for: no `200`, no `4xx` or `5xx`, no timeout. The
whole probe step finished in under six seconds, inside its ten-second limit.

The failure falls inside the container swap of that deploy. No witness run was
watching this swap, so how long it actually dropped requests was not measured.

**Cause:** the probe's single request landed in the container swap of
`a66c2f0`. The two hours and seventeen minutes after it are the gap in the
schedule.
**Fix:** nothing on the site yet. The probe gap is #505.

## INC-003 · 10 October, 22:06:52Z

The probe got a `4xx`. Nothing was deployed that evening and nothing was
committed. It has the same signature as INC-001, but it was not checked at the
time.

**Cause:** not determined. A `4xx` at 22:06:52Z with no deploy and no commit
behind it.
**Fix:** #505.

## What stays

The five cells stay red. They are what the probe measured, and changing a
measurement because its explanation is kinder would be the exact thing this
site is built against. With this entry each of them now carries a notch that
leads here.
