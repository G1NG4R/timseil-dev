2aSchichtenbild · 1440 — von vorne nach hinten: Browser, DNS, Proxy, Frontend, API, Datenbank, Speicher
MAP.03 SCHICHTEN — VORNE NACH HINTEN 7 SCHICHTEN · SPRACHE UND ROLLE PRO SCHICHT
JE WEITER EINGERÜCKT, DESTO WEITER HINTEN — nur die oberste Schicht sieht der Besucher SPRACHE ALS CHIP · EXTERN ALS WORT
VORNE HINTEN
01 · BROWSER HTML · CSS · WENIG JS BEIM BESUCHER
Bekommt fertiges HTML und ein kleines Bündel JavaScript für Terminal, Filter und das 404-Spiel. Kein Framework-Ballast, keine Einbettung von außen.
02 · NAMENSAUFLÖSUNG DNS · A-RECORD EXTERN · REGISTRAR
Name auf Adresse, ohne Proxy dazwischen. Das ist eine Entscheidung: kein CDN im Anfrageweg, also kein Dritter, der Besucherdaten sieht — und kein fremder DDoS-Schutz.
03 · EINGANG TRAEFIK · GO-BINARY TLS · ACME EIGEN · CONTAINER 1 — PROXY
Beendet TLS, verteilt nach Route, schreibt für jede Anfrage eine Log-Zeile. Diese Zeile ist später die Quelle für p95 und Fehlerrate — die Messung kostet keinen zusätzlichen Dienst.
04 · FRONTEND TYPESCRIPT NEXT.JS APP ROUTER REACT EIGEN · CONTAINER 2 — WEB
Rendert die Seiten auf dem Server und schickt Markup, nicht Datenbankzugriffe. Was der Browser bekommt, ist bereits fertig — deshalb bleibt die Seite auch ohne JavaScript lesbar.
05 · API TYPESCRIPT GO SQLITE-AGGREGAT EIGEN · CONTAINER 2 + 3 — WEB, HEALTH
/api/healtheigener Go-Container: liest das Access-Log, schreibt das SQLite-Aggregat, liefert die Zahlen
/api/contactRoute Handler in TypeScript: prüft Felder, begrenzt die Rate, verschickt Mail
/api/trainingTracks und Belege, Zustand serverseitig abgeleitet
Die API ist die einzige Stelle, die Daten liest oder schreibt. Nichts auf der Seite hat einen zweiten Weg zur Datenbank — deshalb kann Angezeigtes nicht von Gemessenem abweichen.
06 · DATEN SQL POSTGRES 16 EIGEN · CONTAINER 4 — DATENBANK
Postgres hält, was sich im Betrieb ändert: Systeme, Tracks, Belege, Vorfälle, Deploys. Texte liegen als MDX im Repo, das Betriebsaggregat als SQLite-Datei beim Health-Container. Kein Zugriff von außen, nur über die API — Details in 2b.
07 · UNTEN UND DANEBEN EXTERN · 4 DIENSTE
Monitorprüft von außen, jede Minute
Actionsbaut, testet, ruft den Webhook
S3nächtliche Sicherung, 30 Tage
MailFormularversand, Anbieter offen
EINE ANFRAGE, DURCH ALLE SCHICHTEN
01 → 02 → 03 → 04 → 05 → 06 und zurück. Alles auf einem Host, vier Container, ein Netz.
WAS DER BROWSER NIE SIEHT
Datenbank, Aggregat, Panel, Log. Nach außen sind nur 80 und 443 offen, alles andere hört nur im Docker-Netz.
SPRACHEN, EHRLICH GEZÄHLT
TypeScript für Seite und Handler, Go für den Health-Dienst, SQL für die Abfragen. Alles andere ist Konfiguration.

WIE AUS ZEILEN ZAHLEN WERDEN
▸ uptime = 1 − Σ down_sec / (gemessene Tage × 86400)
▸ p95 = p95 über die samples des Fensters
▸ MTTR = Σ duration_sec / Anzahl incidents
▸ track.state = 0 Belege lernend · 1 applied · ab 2 core
▸ fehlt eine Zeile: — NO DATA, nie 0 und nie 100 %
DIE LEERSTELLE KONTAKTNACHRICHTEN
Es gibt keine Tabelle dafür. Eine Nachricht wird geprüft, per Mail verschickt und dann vergessen; die IP für das Rate-Limit steht zehn Minuten im Arbeitsspeicher und nirgends auf der Platte. Genau so steht es in der Datenschutzseite — die Datenbank ist der Beleg dafür.
TRENNUNG MIT GRUND
Inhalte sind wertvoll und werden gesichert. Betriebswerte sind nachrechenbar — dafür braucht es keine zweite Postgres-Instanz.
KEIN ZUSTAND OHNE ZEILE
tracks kennt kein state-Feld und days kein uptime-Feld. Beides wird gerechnet, damit Anzeige und Wahrheit nicht auseinanderlaufen.
VORSCHLAG, NICHT GESETZ
Die Spalten folgen den Datenverträgen in README 9.1 bis 9.5. Wer beim Bauen umbenennt, ändert dort mit.
