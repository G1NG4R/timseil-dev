Go concurrency patterns in production

Worker pools, bounded queues, and what actually breaks under load — starting with the goroutine leak that took my own API down.

SUMMARY

One goroutine per feed item is fine until a slow host holds a thousand of them open. The fix was not a bigger box: it was a bounded pool, a queue with a depth I watch, and a memory limit that turns a leak into a restart instead of an outage.

01The failure

Feedhound polls a list of RSS sources on a schedule. The first version did the obvious thing: for every source in the list, start a goroutine, fetch, parse, write. On my machine with twelve feeds it finished in under a second, so I shipped it.

In production the list grew and one host started answering in forty seconds instead of two hundred milliseconds. Every poll cycle stacked another set of goroutines on top of the ones still waiting, each holding a parsed document in memory. The container hit its limit and restarted mid-write.1

POSTMORTEM · INC-001
The leak was not the bug. The bug was that nothing limited concurrency, so one slow dependency could consume the whole process. A restart loop is what a missing bound looks like from the outside.

02A pool, not a goroutine per item

The replacement is unremarkable, which is the point. A buffered channel acts as a semaphore, errgroup collects the first error, and the number of workers is a config value rather than a property of the input.

// one bounded pool per cycle — limit comes from config, not the input

func (w *Worker) Run(ctx context.Context, feeds <-chan Feed) error {
    sem := make(chan struct{}, w.limit)
    var g errgroup.Group

    for f := range feeds {
        f := f
        sem <- struct{}{}          // blocks once limit is reached
        g.Go(func() error {
            defer func() { <-sem }()
            return w.fetch(ctx, f)
        })
    }
    return g.Wait()
}

03Backpressure is the real fix

A pool caps how much work runs at once, but it says nothing about how much work is waiting. That is the number that predicts trouble, so the queue got a fixed capacity and a metric.

A queue without a limit is not a queue. It is a slower way to run out of memory.

When the queue is full, new work is dropped and counted rather than accepted and forgotten. Dropping visibly is better than degrading invisibly, and the counter is what tells me the poll interval is wrong.

04What I watch now

Four numbers, all cheap to collect, all visible from one command on the host:

[TERMINAL CAPTURE]
QUEUE DEPTH · WORKERS · DROPPED · CYCLE MS
01Queue depth. If it never reaches zero within a cycle, the interval is too short for the source list.
02Workers busy. Pinned at the limit for long stretches means a slow host, not more load.
03Dropped items. Should be zero. Anything else is a decision I need to make consciously.
04Cycle duration, p95. The one number that shows up in the case study for this service.

05What I would do differently

Set the memory limit on day one. The limit did not fix the leak, but it turned a slow death into a fast, obvious restart with a log line I could act on. Everything I learned here came from that log line existing.

I would also have written the metric before the fix. I rebuilt the pool and then spent an evening guessing whether it helped, which is a poor trade against ten minutes of instrumentation.
